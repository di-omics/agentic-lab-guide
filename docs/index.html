Chapter 01

Hamilton STAR and STARlet

You have a Hamilton STAR or STARlet on the bench. This chapter puts an agent in front of it.

Layer 1

Get it going.

Five steps: a Raspberry Pi, your network, one cable, Claude, and an MCP.

What you need

Hamilton STAR or STARletThe instrument.
Raspberry PiWith its power supply and a microSD card. This is the small computer that stays with the instrument.
USB-A to USB-B cableConnects the Pi to the Hamilton. USB-A is the flat plug and goes into the Pi. USB-B is the square plug and goes into the Hamilton.
Ethernet cable or Wi-FiPuts the Pi on your network.
A laptop with Claude CodeWhere you work with the agent.
1

Start with a Raspberry Pi

The Pi is a dedicated computer for the instrument. It sits next to the Hamilton and stays on, so the agent always has a way in and your laptop can come and go.

Install Raspberry Pi OS on the microSD card with the Raspberry Pi Imager. In the Imager's settings, give the Pi a hostname, create a user, and turn on SSH. This guide uses the hostname star-pi.

2

Get it connected and configured on your network

Plug the Pi into your network with the Ethernet cable, or use the Wi-Fi you set in the Imager. Power it on, then reach it from your laptop:

ssh <user>@star-pi.local

Once you are in, bring it up to date:

sudo apt update
sudo apt upgrade
3

Cable the Hamilton to the Pi

Connect the USB-A to USB-B cable: flat plug into the Pi, square plug into the Hamilton. Power the Hamilton on.

Let users on the Pi talk to USB devices. Add these two lines to /etc/udev/rules.d/99-usb.rules:

SUBSYSTEM=="usb", MODE="0666"
SUBSYSTEM=="tty", MODE="0666"

Then reload the rules and check that the Pi can see the instrument:

sudo udevadm control --reload-rules && sudo udevadm trigger
lsusb

These rules open every USB device on the Pi to its users, which is fine for a Pi you control. They come from the PyLabRobot Raspberry Pi guide.

4

Have Claude install PyLabRobot and write the driving approach

PyLabRobot is the open-source Python library that talks to the Hamilton. From here on you do not type commands. You ask Claude, and Claude works on the Pi over SSH.

First, the install.

Say to Claude

You can reach a Raspberry Pi with ssh <user>@star-pi.local. It is connected by USB to a Hamilton STAR. On the Pi, make a project folder with a Python virtual environment and install PyLabRobot with USB support. Tell me which version you installed.

Then the driving approach: a short plan for how the agent will drive this instrument, written before it drives anything.

Say to Claude

Read the PyLabRobot source you just installed, not your memory of it. Then write a one-page driving approach for this Hamilton STAR: how you will connect, how you will initialize, what you will run first, what you will never run without asking me, and how a run is stopped. Do not move the instrument yet.

Then the first connection, with you at the instrument.

Say to Claude

Write the smallest script that connects to the STAR, initializes it, and stops. Show it to me before you run it. I am standing at the instrument.

5

Make an MCP that connects your company's context to the instrument

So far the instrument answers to one person at one terminal. An MCP changes that. MCP, the Model Context Protocol, is an open standard for connecting AI applications to outside systems. An MCP server on the Pi offers the instrument as a set of tools, and each tool is something PyLabRobot can do.

Once it exists, the agent that already holds your company's context can reach the PyLabRobot that drives the instrument.

Say to Claude

Build a small MCP server on the Pi around the script you just wrote. Start with tools for what already works: connect, initialize, and stop. Any tool that moves the instrument waits for my confirmation. Then show me how to add this server to our company's agent.

For a worked example of PyLabRobot behind MCP tools, see plr-mcp.

Layer 1 is done when

Your agent, with your company's context, can connect to the instrument through the MCP, initialize it, and stop it, while you watch.

Stay at the instrument. A liquid handler has moving parts. Someone watches the deck for every run and knows how to stop it. PyLabRobot drives the STAR through its firmware, and its authors are plain that you use the driver at your own risk and that warranty is between you and your vendor.
